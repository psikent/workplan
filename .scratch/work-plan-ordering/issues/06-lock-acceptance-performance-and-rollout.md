# 锁定验收、性能与上线边界

Type: grilling
Status: resolved
Blocked by: 02, 03, 04, 05

## Question

完整排序规格需要覆盖哪些自动化和浏览器验收矩阵，目标数据规模、查询与导出性能预算是什么，旧客户端兼容与上线观察窗口如何判定完成，出现排序或分页回归时怎样回退？

## Answer

- 标准性能数据集固定为 100,000 条工作计划、50 个启用的自定义字段，并包含已归档字段、重复实例、四种有效状态、高比例缺失值、中文与数字混合文本、失效单选值、跨日和边界时间。测试必须覆盖最多五个显式排序字段及全部相等后的排期兜底。
- 服务端自动化至少覆盖：
  - 每种可排序字段的升降序、缺失值、自然文本、状态业务顺序、单选配置顺序、稳定兜底和非法字段。
  - 半开时间范围、午夜、跨日、手动状态、三个工作台计划区块、提醒可重复及第七个工作日边界。
  - 首尾页、空页、相同值、无效/错配游标，以及翻页间新增、删除和改变排序位置的实时视图行为。
  - 准确总数、同一求值时刻、旧 offset 兼容、列表/搜索/导出共用语义。
  - `sortOrder` 墓碑路由、公共契约停止输出、旧 JSON 备份导入和最终删列迁移；自定义字段排序必须有明确防回归测试。
- 浏览器验收覆盖 Administrator、Editor、Viewer，桌面和 `<=720px` 窄屏，鼠标和纯键盘：默认排期、多字段增删/调序/方向、URL 直达与历史、账户隔离偏好、归档字段降级、加载/失败/重试、表格与甘特结果一致，以及 XLS 顺序与当前已生效查询一致。Token-only Account 不进入 Web 矩阵。
- 在与生产相当的单实例 SQLite 环境、预热数据库和标准数据集上，性能门槛为：
  - 包含准确总数的首个或后续 100 条查询，p95 不超过 500 ms、p99 不超过 1,000 ms。
  - 工作台三个计划区块及其准确计数，p95 不超过 500 ms。
  - 10 个并发只读查询的整体 p95 不超过 1,000 ms，且不得出现数据库忙或 5xx。
  - 导出 100,000 行、25 列 XLS 在 60 秒内完成，进程额外内存峰值不超过 512 MiB；结果行数和顺序必须准确。
  - 用户触发排序后 100 ms 内出现明确加载反馈；最终结果受服务端查询预算约束，不另设伪造的前端完成时间。
- 上线分为查询引擎、Web 使用、兼容观察、数据库删列四个可独立回退阶段。新查询及 UI 上线后开始 14 个连续自然日的兼容观察；期间保留旧 offset API、`sortOrder` 数据库列和重排墓碑路由。
- 观察窗口完成必须同时满足：全部自动化与浏览器矩阵通过；生产查询和导出达到预算；排序/分页相关 5xx 和数据库忙为零；结果错误报告为零；墓碑路由连续 14 天没有调用。若墓碑路由出现调用，先识别并迁移调用方，再重新计算连续 14 天窗口。
- 每个上线阶段记录新旧版本、数据备份、迁移版本和验收结果。删除数据库列前必须完成可恢复备份及迁移演练；迁移在事务中执行，并准备把 `sort_order` 以中性值重新加入的前向修复脚本。删列后若发生排序或分页回归，先停用新 UI/查询入口并切回兼容 API；若旧二进制需要该列，则先执行前向修复再回滚应用，避免用整库回档丢失观察期间的新业务数据。仅在迁移本身破坏数据时恢复删除列前的完整备份。
- 任一门槛未满足都停止推进下一阶段，不以扩大超时、降低断言、关闭准确计数或重新引入人工 `sortOrder` 作为验收方式。
