# 定义查询分页与并发契约

Type: grilling
Status: resolved
Blocked by: 01

## Question

统一查询引擎应提供怎样的请求与响应契约：精确字段白名单、自然文本比较的一致实现、不透明游标内容、准确总数和求值时间；数据在翻页之间发生新增或修改时保证什么、不保证什么；GET 列表和现有 offset 调用如何兼容？

## Answer

- 服务端提供一个统一工作计划查询引擎，工作计划页、列表、搜索、筛选与 XLS 导出都调用它；工作台和提醒可复用其统一排期比较语义，但保留各自的入选与分组规则。
- 新增 `POST /api/v1/work-plans/query` 作为游标契约。请求包含可选全文搜索、过滤条件、零至五个有序排序项，以及 `limit` 和可选 `cursor`；`limit` 范围为 1–500。`cursor` 与任何 offset 参数互斥，同时出现时返回参数错误。
- 显式排序字段白名单固定为：`title`、`status`、`startAt`、`endAt`、`duration`、`createdAt`、`updatedAt`，以及 `custom.<key>` 形式的短文本、数字、布尔、日期、日期时间、单选和 URL 自定义字段。说明、重复来源、版本、内部 ID、工作负责人账号、长文本和多选不可排序；未知、重复、归档或类型不支持的字段返回稳定的 400 参数错误，不静默忽略。
- 状态升序固定为待开始 → 进行中 → 已完成 → 已取消，降序只反转这四个状态的业务顺序；持续时长按 `endAt - startAt` 的数值比较；日期时间按绝对时间点，日期按 `Asia/Shanghai` 日历日，URL 与短文本使用同一自然文本比较。所有显式字段相等后始终按排期顺序兜底，兜底不随最后一个显式字段反转。
- 每个响应为 `{ items, total, evaluatedAt, nextCursor }`：`items` 是当前页，`total` 是同一请求求值下过滤结果的准确总数，`evaluatedAt` 是服务端捕获的 ISO 时间点，末页的 `nextCursor` 为 `null`。计数与当前页读取在同一数据库读事务中完成。
- 不透明游标由服务端生成并验证，带契约版本、查询条件指纹、规范化显式排序项，以及上一条记录在每个显式排序字段、排期兜底字段和最终 ID 上的规范化位置。客户端只能原样回传；格式错误、版本不支持或查询指纹不匹配均返回 400，不尝试猜测或修复。
- 所有文本在服务端使用同一套固定中文自然比较语义：Unicode 规范化、忽略大小写、识别数字；数据库查询、游标定位和导出必须共享同一比较实现及金样测试。空值、空白文本和失效单选项统一作为缺失值，升降序均置后。
- 游标分页提供实时视图，不创建跨请求快照。未改变排序位置的既有记录不会因其他记录插入而产生 offset 漂移；但记录在翻页间被新增、删除或修改排序字段后，可能移动到游标前方、从后方消失或再次越过边界。接口不承诺跨页无遗漏或绝对去重，用户从第一页刷新是重新同步的唯一方式。
- 旧 `GET /api/v1/work-plans` 与 `POST /api/v1/work-plans/search` 在兼容期内保留原有数组响应、`limit`/`offset` 和已有筛选参数，但内部改走统一查询引擎，并使用新的排期顺序作为默认顺序。旧调用不获得游标一致性保证；新页面和新集成只使用 `/query`。
- XLS 导出不接收页面游标，也不受页面 `limit` 限制；它在单次数据库读事务中用同一查询条件和排序从头求值并读取完整结果。
