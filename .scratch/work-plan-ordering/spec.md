# Spec: 工作计划统一排序与游标查询

> Status: **待批准实施** — 排序决策已经闭合，实施票据已经形成；在用户明确批准本规格前，不修改应用代码、数据库或生产环境。

## Goal

为所有工作计划读取场景建立同一套可解释、稳定且可扩展的排序体系：每个场景先决定成员和分组，再应用场景主序，最后使用统一排期顺序稳定兜底。工作计划页的表格、甘特图、搜索、分页和 XLS 导出由服务端统一查询结果驱动，并逐步退出含义冲突的工作计划人工 `sortOrder`。

## Current Gaps

- 普通列表在 SQL 中按开始、结束、重复来源、`sortOrder` 和 ID 排序；共享前端比较器采用类似但不完全相同的规则。
- 搜索先读取最多 10,000 条工作计划，再在 Node.js 内存中过滤、排序和 offset 分页；不提供准确总数。
- 工作计划页一次读取最多 500 条，并在浏览器内再次过滤和排序；表格、甘特图和导出缺少统一服务端权威结果。
- 工作台分组、提醒与导出各自维护局部成员或顺序规则。
- `POST /api/v1/work-plans/reorder` 和数据库 `work_plans.sort_order` 仍存在，但当前页面没有工作计划人工排名入口；该序号也不等于实际显示顺序。
- 当前 `better-sqlite3 12.11.1` 的 JavaScript API没有注册自定义 collation 的能力，当前 SQLite 构建也没有 ICU；中文自然排序必须先验证可索引排序键或其他可部署方案，不能退回十万行全量内存排序。

## Domain and Boundaries

- 用户可见的工作项统一称为 Work Plan（工作计划），不引入独立“任务”概念。
- Work Plan Time Range（工作计划时间范围）是 `[startAt, endAt)` 半开区间；涉及本地日期时使用 `Asia/Shanghai`。
- Schedule Order（排期顺序）是系统默认和所有场景的稳定兜底，不是人工优先级。
- 自定义字段定义、自定义字段选项、表格列、甘特显示属性和导出列自身的排列不属于工作计划排序；它们现有的 `sortOrder` 保持不变。

## Query Pipeline

所有读取场景按固定流水线执行：

1. **入选**：根据场景、全文搜索、筛选和时间窗口选出工作计划。
2. **分组**：只有工作台和提醒需要业务分组；普通列表、搜索和导出不分组。
3. **场景主序**：工作计划页可使用用户显式排序；提醒先按提醒类型；其他场景使用自己的已定主序。
4. **排期兜底**：所有并列最终回退到统一排期顺序。
5. **分页或导出**：页面查询使用游标，导出从头读取完整结果。

任何前端组件不得在服务端结果返回后重新定义工作计划顺序。

## Schedule Order

排期顺序固定为：

1. `startAt` 升序；
2. `endAt` 降序；
3. `createdAt` 升序；
4. `id` 升序。

重复规则或实例来源不构成优先级。显式排序全部相等后使用完整排期顺序，兜底方向永远固定，不随最后一个显式字段反转。

## Scenario Semantics

| 场景 | 入选/分组 | 主序 | 最终兜底 |
| --- | --- | --- | --- |
| 工作计划页表格与甘特图 | 相同搜索、筛选与时间范围 | 用户零至五个排序字段；零个即排期顺序 | 排期顺序 |
| 今日新开工 | 开始本地日为今天，且未取消；包括今天已完成 | 无额外主序 | 排期顺序 |
| 今日继续开工 | 开始本地日早于今天、范围与今天相交，且未完成、未取消 | 无额外主序 | 排期顺序 |
| 接下来的计划 | 开始本地日在明天至第七个工作日之间，且未完成、未取消 | 无额外主序 | 排期顺序 |
| 今日提醒 | 提醒规则独立入选；允许与计划区块重复 | 检修单提醒先于作业计划提交提醒 | 同类提醒内按排期顺序 |
| 列表与搜索 API | 请求查询条件 | 请求显式排序；缺省为排期顺序 | 排期顺序 |
| XLS 导出 | 重新执行页面完整查询，不受页面游标限制 | 页面已经成功应用的排序 | 排期顺序 |
| 重复计划实例 | 与普通工作计划相同 | 不因重复来源获得优先级 | 排期顺序 |

JSON 业务备份只保证数据语义，不保证数据库表物理行序。

## Workbench Date Rules

- 本地日历日表示为 `[当日 00:00, 次日 00:00)`；工作计划与某日相交，当且仅当 `startAt < 次日 00:00` 且 `endAt > 当日 00:00`。
- 恰好在 00:00 结束的工作计划不占用新的一天；恰好在 00:00 开始的工作计划属于新的一天。
- 三个计划区块使用同一求值时刻并且互斥；一条工作计划最多进入其中一个。
- 手动状态覆盖自动状态。手动完成只允许出现在开始日为今天的“今日新开工”；手动取消不进入任何计划区块。
- Upcoming Window（接下来的窗口）从明天开始，以向后数第七个 Working Day 为包含式终点，并包含中间周末。
- 今日提醒是独立关注面；同一工作计划可同时出现在提醒和一个计划区块中。

## Sortable Fields

用户最多提供五个有序、互不重复的排序项，每项独立指定 `asc` 或 `desc`。

| 字段 | API 键 | 比较语义 |
| --- | --- | --- |
| 工作内容 | `title` | 固定中文自然文本比较 |
| 状态 | `status` | 升序：待开始 → 进行中 → 已完成 → 已取消；降序反转 |
| 开始时间 | `startAt` | 绝对时间点 |
| 结束时间 | `endAt` | 绝对时间点 |
| 持续时长 | `duration` | `endAt - startAt` 数值 |
| 创建时间 | `createdAt` | 绝对时间点 |
| 更新时间 | `updatedAt` | 绝对时间点 |
| 短文本、URL | `custom.<key>` | 固定中文自然文本比较 |
| 数字 | `custom.<key>` | 数值比较 |
| 布尔 | `custom.<key>` | 升序为未勾选后已勾选；降序反转 |
| 日期 | `custom.<key>` | `Asia/Shanghai` 日历日 |
| 日期时间 | `custom.<key>` | 绝对时间点 |
| 单选 | `custom.<key>` | Administrator 配置的选项顺序 |

说明、重复来源、版本号、内部 ID、工作负责人账号、长文本和多选不可排序。

空值、空白文本和失效单选项统一视为缺失值，升序和降序均置后。未知、重复、归档或类型不支持的字段返回明确参数错误，不静默忽略。

中文自然文本比较必须具备以下可观察性质，并由金样测试固定：Unicode 规范化、忽略大小写、数字片段按数值、结果为稳定全序。具体排序键方案由实施票据 08 原型验证；数据库查询、游标定位、共享比较器和导出必须使用同一语义。

## Work Plan Page Sorting UI

- 页面提供独立“排序”面板；没有排序项时显示“排期顺序（默认）”。
- 用户可添加、删除、上移、下移排序项并切换方向；从上到下是优先级。恢复默认会清空显式排序项。
- 表格与甘特图共享同一查询结果；切换视图、时间范围或打开详情不重置排序。
- URL 规范格式为 `sort=<field>:<direction>,<field>:<direction>`，例如 `sort=title:asc,custom.risk:desc`。默认排期顺序不写该参数。
- 状态优先级为合法 URL → 当前账户浏览器偏好 → 默认排期顺序。偏好按稳定账户 ID 隔离并带版本；URL 只覆盖当前导航，用户主动修改后才保存偏好并更新 URL。
- 非法 URL 整体回退到排期顺序并显示说明；本地偏好逐项清理失效字段并提示一次。直接 API 请求始终返回错误，不使用界面降级规则。
- 请求期间保留上次成功结果并显示加载；失败时保留结果、排序选择和页面上下文，提供内联错误与重试，不把未成功状态用于导出。
- 桌面和窄屏提供相同能力；排序不得只依赖拖动。上移、下移、移除和方向控件必须可聚焦、有明确标签和状态反馈。
- Administrator、Editor 和 Viewer 均可排序；Token-only Account 没有 Web 工作台。

## Query API Contract

新增 `POST /api/v1/work-plans/query`。请求概念结构为：

```json
{
  "q": "可选全文搜索",
  "filters": [],
  "range": { "from": "可选 ISO 时间", "to": "可选 ISO 时间" },
  "sort": [{ "field": "title", "direction": "asc" }],
  "limit": 100,
  "cursor": "可选不透明游标"
}
```

- `q`、筛选操作和字段继续遵循既有业务能力；时间范围采用半开相交语义。
- `sort` 最多五项；`limit` 为 1–500，默认 100。
- `cursor` 与任何 offset 参数互斥。
- 响应固定为 `{ items, total, evaluatedAt, nextCursor }`。`total` 是同一请求求值下的准确总数，`evaluatedAt` 是服务端 ISO 时间，末页 `nextCursor` 为 `null`。
- 当前页和准确总数在同一数据库读事务内求值。

不透明游标至少绑定：契约版本、查询条件指纹、规范化排序描述，以及上一条记录的显式排序位置、完整排期兜底位置和最终 ID。客户端只能原样回传。格式错误、版本不支持或查询指纹不匹配返回稳定的 400 错误。

建议稳定错误类别包括：非法排序字段、重复排序字段、不支持的排序类型、非法游标、游标与查询不匹配，以及工作计划重排已退役；具体响应外壳遵循现有错误约定。

## Pagination and Concurrency

- 游标分页是实时视图，不创建跨请求历史快照。
- 在既有记录排序位置不变时，键集游标避免 offset 因其他记录插入而整体漂移。
- 若记录在翻页间新增、删除或修改排序字段，它可能移动到游标前、从后续页消失或再次越过边界；接口不承诺在变化数据上的跨页绝对无遗漏或无重复。
- 用户从第一页刷新是重新同步实时结果的唯一方式。
- 旧 `GET /api/v1/work-plans` 和 `POST /api/v1/work-plans/search` 在兼容期保留数组响应与 offset 参数，但内部必须调用统一查询引擎，并使用新排期顺序作为默认值。新页面和新集成只使用 `/query`。

## XLS Export

- 从工作计划页发起的 XLS 导出携带页面当前已经成功应用的搜索、筛选和排序描述，不携带页面游标。
- 服务端在一个数据库读事务中从头重新执行完整查询，导出全部命中项并返回准确顺序。
- 导出不受页面 `limit`、当前页或旧 500/10,000 条读取上限影响。
- 导出列的选择和排列仍由现有 XLS 模板/页面属性控制，不属于工作计划行排序。

## Work Plan `sortOrder` Retirement

自定义字段及其选项的 `sortOrder` 永久保留。工作计划 `sortOrder` 分四阶段退出：

1. 统一查询引擎和所有消费者停止读取工作计划 `sortOrder`；新建工作计划仅向遗留列写中性兼容值。
2. 公共 Work Plan 响应停止输出该字段，公开重排请求契约移除；旧重排路由成为无副作用的 `410 Gone` 墓碑并记录调用计数。
3. 保留数据库列和版本 1–4 JSON 备份兼容至少 14 个连续自然日；观察完成条件见下文。
4. 观察通过后重建 `work_plans` 表，删除列与索引，并升级 JSON 备份版本；新导入器继续接受旧备份并忽略遗留值。

旧 `sortOrder` 数值不迁移到新排序偏好，不映射为任何业务优先级。

## Performance and Acceptance Budget

标准数据集：100,000 条工作计划、50 个启用自定义字段，并覆盖归档字段、重复实例、四种状态、高缺失率、中文数字混合文本、失效单选值和边界时间。

在生产同等级单实例 SQLite 环境、预热数据库上：

- 含准确总数的首个或后续 100 条查询：p95 ≤ 500 ms，p99 ≤ 1,000 ms。
- 工作台三个计划区块及准确计数：p95 ≤ 500 ms。
- 10 个并发只读查询：整体 p95 ≤ 1,000 ms，数据库忙和 5xx 为零。
- 100,000 行、25 列 XLS：≤ 60 秒，进程额外内存峰值 ≤ 512 MiB。
- 用户触发排序后 100 ms 内出现加载反馈。

自动化必须覆盖所有字段比较、缺失值、状态顺序、排期兜底、半开边界、工作台、提醒、游标、准确总数、并发变化、旧 offset、导出、墓碑路由、旧备份和最终删列。浏览器矩阵覆盖三种 Web 角色、桌面/窄屏、鼠标/键盘、URL/偏好、加载/失败、表格/甘特和导出一致性。

## Rollout and Rollback

上线按查询引擎、Web 使用、兼容观察、数据库删列四阶段推进。每阶段必须独立可回退并记录版本、数据备份、迁移版本和验收证据。

兼容观察从新查询和 Web 排序在生产启用后开始，持续 14 个连续自然日。结束条件：

- 自动化、浏览器和性能门槛全部通过；
- 排序/分页相关 5xx、数据库忙和已确认结果错误均为零；
- 重排墓碑路由连续 14 天没有调用。

墓碑路由出现调用时，先识别并迁移调用方，再重新计算 14 天。

删除数据库列前必须完成可恢复备份和迁移演练。迁移在事务中执行，并准备将 `sort_order` 以中性值重新加入的前向修复。删列后若回归，先停用新 UI/查询入口并切回兼容 API；旧二进制需要该列时先执行前向修复再回滚应用，避免整库回档丢失新业务数据。只有迁移本身破坏数据时才恢复完整备份。

不得通过扩大超时、降低断言、关闭准确总数或重新引入人工 `sortOrder` 来通过门槛。

## Out of Scope

- 月度目标、自定义字段定义、自定义字段选项、表格列、甘特显示属性和导出列自身的排序。
- 工作计划拖动排名、人工优先级或把旧 `sortOrder` 转换为偏好。
- JSON 备份中的数据库物理行序。
- 跨分页请求的历史快照或强一致会话。
- 为 Token-only Account 新增 Web 工作台。
- 在本规格获批前修改业务代码、迁移数据库、提交、推送或发布。

## Acceptance Criteria

1. 所有读取场景都能说明入选、分组、主序、排期兜底和分页/导出步骤。
2. 排期顺序严格为开始升序、结束降序、创建升序、ID 升序，不含重复来源或人工序号。
3. 三个工作台计划区块在半开边界下互斥，提醒可以与计划区块重复。
4. 所有可排序字段、方向、缺失值、状态顺序和非法参数行为符合本规格。
5. 工作计划页可管理最多五级排序，URL、账户偏好、降级、加载、失败和无障碍行为完整。
6. 表格与甘特使用同一服务端结果，前端不二次排列工作计划。
7. `/query` 返回准确总数、求值时间和可验证的不透明游标，静态数据分页无遗漏、无重复。
8. 数据变化时的实时视图限制有自动化证明，刷新能从第一页重新同步。
9. 旧 list/search offset 调用在兼容期保持响应形状并改走统一引擎。
10. XLS 完整复用页面已生效查询与排序，不受页面条数限制。
11. 工作计划公共契约停止输出 `sortOrder`，旧重排路由无副作用并可观测；自定义字段排序无回归。
12. 十万条标准数据集上的查询、并发、工作台和导出达到性能预算。
13. 生产观察连续 14 天满足所有门槛后，才允许执行最终数据库删列票据。
14. 全仓 typecheck/test、性能测试和真实浏览器验收通过，证据记录在对应票据。
